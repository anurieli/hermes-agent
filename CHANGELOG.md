## 2026-08-07

- Added per-assignee **delivery contract** gates to the kanban layer. A profile can declare `kanban.delivery_contract.enabled: true` in its config.yaml, and three verbs then acquire hard preconditions in `kanban_db.py` itself, the one chokepoint every caller shares (agent tools call the DB in-process, so CLI-only or tool-only gates do not cover agents): `complete_task` refuses a completion whose summary/result carries no handoff (no PR URL, no already-delivered evidence citing a commit, no explicit cancel), with a `completion_blocked_contract` audit event before the raise; `block_task` refuses an empty reason and any reason matching work-not-decision patterns (stale base branch, the worker's own review findings); `archive_task` refuses to archive a task that never completed unless `force=True` (new `--force` flag on `hermes kanban archive`). Gates key on the TASK'S assignee profile config via the context-local home override, so re-invoking under a different HERMES_HOME does not shed them. `HERMES_KANBAN_CONTRACT_OVERRIDE=1` disables all three for deliberate human action. Refusal messages are written for the worker model to read mid-task: each states exactly what to do instead. Motivation: all three rules lived in an agent's prompt and were violated anyway (a completion with an unpushed branch, three blocks on the worker's own work, five unfinished tasks bulk-archived in one second to dodge a question).
- Dispatcher now injects a **resume stance** into the worker prompt when a task has prior closed runs: attempt number, and an instruction to treat the worktree and comment history as its own past work, continue, and not re-plan or re-audit. A fresh model instance's default is to distrust the previous instance's work; that instinct is how resumed tasks re-litigate themselves instead of finishing. Fixed the direct-launch guard in `cli.py` from `re.fullmatch` to a prefix `re.match` in the same change, since any prompt suffix would otherwise silently disable that guard.
- Committed alongside (previously uncommitted on this deployment): the task-containment work from 2026-08-02: `HERMES_KANBAN_DISPATCHED=1` launch marker with a fail-closed guard against direct `work kanban task` launches, systemd-run transient scopes per worker, and `HERMES_KANBAN_DEFAULT_MAX_RUNTIME_SECONDS` / `_MAX_RETRIES` env defaults in `create_task`. Updated `hermes_cli/kanban_db.py`, `hermes_cli/kanban.py`, `cli.py`.

## 2026-08-05

- Fixed a Slack Socket Mode failure that made an agent go permanently deaf while every health signal stayed green. `slack_sdk`'s `AsyncSocketModeClient.connect()` is an unbounded `while True` whose only exit is a successful `ws_connect`; it never consults `self.closed`, so a reconnect in flight when the client closes keeps retrying against the closed aiohttp session every `ping_interval`, forever. Cody hit this on 2026-08-03: last inbound Slack message 08:27, then ~1,500 retries at a 10-second cadence over 43 hours with zero adapter-level restarts. The gateway stayed `active (running)`, `NRestarts` stayed 0, and outbound `chat.postMessage` kept working on a separate client, so his hourly alerts still arrived and nothing looked broken. Added `_harden_socket_client`, which supervises `connect()` and cancels the retry task once the client is closed, turning an invisible infinite loop into a normal exception the adapter watchdog can act on. Reordered `_stop_socket_mode_handler` to cancel our task *before* closing the handler, so the loop unwinds while its session is still valid, and to unconditionally cancel the client-internal futures that `close()` only cancels on a clean run. Updated `plugins/platforms/slack/adapter.py`.
